Pull It Together / Case study 02

Shared gameplay.
Responsive presentation.

Connecting host authority, local visuals, and the many states of a cooperative interaction.

My role: system design & implementationGodot · C# · GDScriptMultiplayer gameplay

One interaction, several responsibilities.

A held tool has to exist in the shared world and also look connected to the player holding it. The same object may move between the ground, a hand, inventory, and the wagon. Ropes and cooperative carrying add more relationships to preserve.

I built the item and entity authority framework, interaction handling, held-state reconstruction, and visual synchronization supporting these transitions. The design separates shared gameplay decisions from how motion is presented locally.

Architecture decision

Keep gameplay state authoritative.

The host assigns unique object identities and handles gameplay requests such as pickup, drop, inventory changes, and tool use. Those identities give peers a shared way to refer to an object as its state changes. Registration scans designated scene folders, allowing content to enter the same spawning system.

01 / RequestPlayer input

Pick up, drop, use, or move an object.

02 / ResolveHost gameplay state

Validate the request and update the shared object.

03 / PresentLocal visuals

Reconstruct the visible interaction on each peer.

Local held-item representations and visual smoothing address presentation without moving gameplay authority into every visual object. That separation lets me work on attachment and motion while keeping a single source for the shared state.

Joining is a state transition, too.

A new peer needs more than a list of spawned objects. It needs to reconstruct the current relationships: which objects exist, which are held, and which state belongs to the current connection.

The framework uses session-aware world snapshots, acknowledgments, and held-state reconstruction. Session tokens distinguish a current connection from stale messages, and cleanup removes obsolete registrations and local proxies as peers leave.

This makes joining part of the same interaction architecture, rather than a separate visual shortcut.

Animate from gameplay parameters.

Movement blends, interaction selections, and action-speed parameters drive animation graphs locally. The animation layer works alongside object replication so that locomotion, aiming, item use, and held-object presentation describe the same action.

Spend work where the players are.

I also built world-interest handling for spatial dormancy, per-peer synchronization visibility, and waking objects for interactions. Motion updates and changed state use distinct replication policies. Cleanup behind the storm considers proximity to players before removing eligible objects.

These mechanisms support the same goal as the interaction framework: keep the active cooperative space responsive while preserving the state players rely on. Navigation chunks around the wagon apply a similar focus to animal movement through the generated environment.

Iterate on the player-facing result.

Recent work includes reducing item clipping at the back of the wagon on clients and giving a carried player a timed “wiggle out” action with input instructions. These are small interactions with consequences for readability and player control.

Across these interactions, I connect the gameplay rule to the state transition and the result players see. Shared object identities and local presentation provide the foundation for that work.
